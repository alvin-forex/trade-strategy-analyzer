## 機理（含一個重要勘誤）

**勘誤**：我之前設計記錄寫「輸出 hex(iv)+hex(cipher)」——**唔完整**。實際讀 `lib/codec.js` 發現 `encodeWithHashedPassword` 外面仲包一層 **HMAC-SHA256**（`signMessage(hashedPassword, encrypted)`，64 hex chars 前綴），`decode()` 先驗簽再解密。wrapper 輸出已正確含 HMAC：

```
hex(HMAC-SHA256(hashedPassword, encrypted))[64] + hex(iv)[32] + hex(cipher)
```

管線與 CLI 逐位同構：
1. `hashPassword(password, salt)` — require 原裝 cryptoEngine（三輪 PBKDF2 共 600k，無改動）
2. `encrypt` — 同 API（subtle AES-CBC＋PKCS#7），**唯一分別**：iv 由 `getRandomValues` 改為 `sha256(明文)[0:16]`
3. `signMessage` — 原裝函數無改動（hashedPassword＋encrypted 都 deterministic → HMAC 也 deterministic）
4. template render — `renderTemplate`（原裝 formater.js）＋`convertCommonJSToBrowserJS`（與 cli/helpers.js L206 同構重寫，因原版綁死 yargs）

**Salt 規則比 CLI 嚴**：必須明確提供（`-s` 或 `TSA_ST_SALT`），**拒絕隨機生成**——CLI 冇 salt 會自己生（寫入 .staticrypt.json），deterministic wrapper 咁做係自毀，所以直接報錯。

## 安全 note（誠實披露 trade-off）

1. **deterministic IV 洩漏相等性**：相同明文→相同密文。呢個正係目的（git 衛生），代價係外部觀察者可比較兩版密文得知「內容有冇變」——本來 git history 就公開呢個資訊，無新增洩漏。
2. CBC＋可預測 IV 嘅選擇明文風險需要攻擊者能控制被加密內容——本場景加密內容全由自家 generator 產生，攻擊面唔存在。
3. salt 固定且**唔係秘密**（CLI 一樣嵌入頁面 config）；安全主柱仍係密碼強度＋600k PBKDF2。
4. **舊 15 頁 remember-me 一次性失效**：舊頁面係 CLI 加密（salt 喺 F1B 嘅 .staticrypt.json），pass 1 見 already-encrypted 會 skip 唔郁佢；當佢哋日後被 generator 重寫再加密，就會轉用新固定 salt——用戶第一次要重入密碼，之後 remember 穩定。
